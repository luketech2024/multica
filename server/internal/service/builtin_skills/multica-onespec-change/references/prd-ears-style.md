# PRD 验收标准写法（中文 EARS）

生成 `prd.md` 时，**§4 及之后**的功能需求验收标准须符合本规范。与 Delta Spec（`onespec-change`）的英文 `*When* … shall` 分工不同：PRD 面向产品/测试评审，**一律中文**。

## 句式（按场景选用）

| 类型 | 模板 | 示例 |
|------|------|------|
| 事件驱动 | 当 **[条件]** 时，**[主体]** 应 **[行为]** | 当并发已达配置上限时，系统应进入等待直至获得配额或超时失败 |
| 状态驱动 | 在 **[持续状态/前提]** 下，**[主体]** 应 **[行为]** | 在 Redis 不可用的情况下，系统应放行本次出站并记录告警 |
| 普遍需求 | **[主体]** 应 **[行为]** | 系统应支持按主体维护多条子接口限额配置 |
| 角色动作 | 当 **[条件]** 时，**[用户角色]** 应能 **[行为]** | 当未创建限流主体时，运营用户应无法提交子接口限额 |

- **主体**：系统、运营用户、测试、运维等，与 PRD 角色定义一致。
- **应**：表示必须满足的需求（对应 EARS / RFC 2119 的 SHALL），不用「须」「必须」混用同一条内多种语气。

## 禁止

- 英文 **`shall` / `SHALL` / `must`**（如 `系统 shall …`）
- 模糊词堆砌：**支持、优化、尽快、尽量**（须改为可验收行为）
- 实现细节：**类名、表名、HTTP 状态码、框架 API**（留在 `design.md` / Delta Spec）

## 与 §0 的分工

- **§0 评审摘要**：口语、列表、表格，不要求 EARS 句式。
- **§4 验收标准**：可测试、无歧义，优先用上表句式编号列出。

## 下游说明

本规范约束 **`onespec-generate-prd` 输出的 `prd.md`**；`onespec-change` 的 proposal/Delta Spec 使用 **中文 EARS** 与 **现状/目标/原因/影响** 四段式，见 `onespec-change` 技能 `change-ears-style.md`。
