# Multica OneSpec 详细设计

设计已确认，已按实现更新 · 2026-11-11

用户已确认本设计。实施计划单独评审，见 [开发计划](tasks.md)。本次开发使用用户指定的 `release_V1.0_vibe-coding` 分支。

依据 [流程方案](platform-workflow.md)、[角色与 Skill 分工](agent-skills.md)、[Git 分支规范](git-workflow.md) 编写。产品方向沿用已确认结论，本文记录实现结构、状态和接口。

## 1. 设计摘要

在现有任务、运行时、系统智能体、Skill 分发和发布执行机制上增加 OneSpec 配置与阶段确认。OneSpec 任务保存独立阶段记录，通过现有任务状态展示整体进度。

平台角色定义随服务发布，执行实例按工作区和运行时配置共享。普通用户创建项目后可以继承默认运行时并使用预置团队。

设计、计划和归档分别确认。阶段产出与确认均关联明确的文档版本。开发维护代码库内的文档，Multica 保存调度记录和文档索引。

首轮交付覆盖完整的轻量开发闭环、发布已有版本路径和独立工程文档路径。其他运行时通过能力验证后开放同一流程。

## 3. 配置与角色

### 3.1 默认运行时

工作区设置增加 OneSpec 默认运行时，仅工作区 owner/admin 可以修改。保存时检查运行时属于当前工作区、调用范围允许团队使用，以及当前操作人有配置权限。

项目提供“继承工作区”和“指定运行时”两种模式。继承模式在创建任务时解析当前默认值，任务保存解析后的运行时。修改默认值影响后续新任务，已有运行继续使用已记录配置。现有未开始且没有产出的任务可以显式更新执行配置并记录审计。

运行时离线可以保存配置，启动阶段执行时显示等待运行时及处理入口。无法获得项目所需权限时明确显示缺口。

### 3.2 平台预置团队

| 角色键 | 显示名 | 执行职责 |
| --- | --- | --- |
| `sched` | OneSpec | 流程协调、交接和状态汇总 |
| `product` | 产品 | 需求与规格 |
| `dev` | 开发 | 设计、计划、实现、缺陷修复和归档 |
| `test` | 测试 | 验证与证据 |
| `ops` | 运维 | 发布准备、部署和运行验证 |
| `docs` | 项目文档 | 独立工程文档任务 |
| `git` | Git 管理 | 分支、工作目录、提交与合并 |

保留现有 `sched` 标识以延续任务和团队引用，显示名称更新为 OneSpec。现有 `sec` 配置和历史结果继续读取，是否参与按任务和项目原有安全规则决定。

角色定义包含稳定 system key、规则版本、默认名称、Skill 清单和默认并发。按工作区、运行时、角色定位实例，创建事务使用确定的唯一键串行处理重复请求。多个用户和项目复用同一可调用实例。

平台规则只读，工作区补充指令单独编辑。实例的技术 owner 记录实际配置者，共享调用范围为该工作区。平台实例配置更新要求工作区管理权限，成员可使用并查看有效配置。

项目切换运行时后解析对应运行时的实例，任务保留既有实例引用。普通自定义智能体可以继续按项目选择，角色用途优先推荐，访问与运行时约束由后端强校验。

### 3.3 代码库配置

项目选择一个已绑定 Git 资源作为总览代码库。保存时校验资源存在且属于该项目。单仓库项目可以直接选择自身。

总览代码库保存项目级需求总览、跨仓库依赖和交付索引，各业务库保存自己的规格、设计、任务与实现记录。总览位于 `onespec/overview.md`，并链接各任务的 `onespec/changes/<issue-id>/` 文档。

创建任务时记录总览代码库和文档路径。项目修改指定代码库后，新任务使用新位置，尚未开始且没有产出的任务可在任务页面更新执行配置，已有产出的任务继续使用原快照。

## 4. 数据结构

采用单独的配置和工作流记录，复用现有 issue、project_resource、agent、agent_task_queue 作为关联对象。所有读写均按 workspace_id 校验作用范围，版本更新使用比较并交换。

| 对象 | 主要字段 | 用途 |
| --- | --- | --- |
| 工作区 OneSpec 配置 | workspace_id、default_runtime_id、revision | 默认运行时 |
| 项目 OneSpec 配置 | project_id、runtime_mode、runtime_id、overview_repository_id、enabled、revision | 项目覆盖与入口 |
| 任务 OneSpec 流程 | issue_id、kind、phase、phase_status、requirement_version、team_snapshot、runtime_id、overview_repository_id、revision | 当前执行状态 |
| 阶段产出版本 | issue_id、stage、version、artifact_refs、input_versions、content_digest、submitted_by、created_at | 可确认的文档与证据 |
| 确认记录 | issue_id、stage、artifact_version、decision、actor_id、actor_role、reason、created_at | 逐项确认及历史 |
| Git 操作记录 | issue_id、repository_id、operation_key、base_commit、branch、worktree、published_commit、merged_commit、status | 分支归属与执行恢复 |

阶段产出引用包含仓库资源 ID、仓库内相对路径、提交 ID 和内容摘要。数据库保存索引和必要的结构化计划，规范正文由代码库保存。首轮界面展示产出摘要、计划条目、文件路径、提交及摘要值。完整文档正文通过代码库查看。

物理存储采用 `onespec_workspace_config`、`onespec_project_config` 和 `onespec_flow` 三张表。阶段产出、确认与 Git 操作保存在单个任务流程的 JSON 聚合中，使用行锁与 revision 比较更新保证原子性。产出版本及操作幂等键由规则层校验，避免一次阶段更新跨多张明细表提交。迁移编号为 660–667。

SQL 迁移与回滚成对提供。唯一性检查覆盖工作区配置、项目配置、任务流程、阶段版本以及 Git 操作幂等键。索引采用仓库要求的独立并发创建迁移，跨对象关系通过事务和应用层校验维护。

## 5. 阶段与状态

`phase` 表示当前环节，`status` 为 preparing、awaiting_confirmation、ready、completed。运行是否排队、执行中或失败仍由现有执行记录展示。

| 工作流情况 | 现有任务状态映射 |
| --- | --- |
| 初始或进入新的待执行阶段 | todo |
| 实现与验证阶段 | in_progress |
| 设计、计划或归档待确认 | 流程面板显示 awaiting_confirmation，任务保留当前执行状态 |
| 成果验收 | in_review |
| 验收确认并推进完成 | done |

每次确认、阶段切换及相关任务变更在事务中提交。缺少配置、权限或证据时保留当前阶段，并显示接口返回的具体原因。

### 5.1 标准开发

规格产出与确认 → 设计产出与确认 → 计划产出与确认 → Git 分支准备 → 实现 → 测试 → 归档清单与确认 → 归档执行 → 验收。发布通过独立发布任务继续追踪。

按任务类型裁剪阶段。简单修改可使用轻量计划，记录省略详细设计的原因。开发计划中每项任务必须覆盖验收条目，角色交接携带同一规格版本。

代码交付任务可以先完成自身验收，通过关联发布任务继续追踪部署和回合。代码进入 `release` 遵循发布后回合规则。无部署交付需求的独立文档任务按文档审查与合并完成。

### 5.2 发布已有版本

发布目标确认 → 发布准备与草稿 → 发布中心配置、授权与部署 → 部署结果确认 → 回合方案确认 → 回合执行 → 验收。任务页面可选择 staging 或 prod 环境并创建草稿，默认选中 staging。部署证据只能关联已上线的发布单，确认时重新校验发布单 revision。

服务器、域名和凭证在对应部署动作执行前校验。发布草稿允许缺少这些配置。目标和完成标准明确后可进入发布准备，OneSpec 将缺失项列入发布配置。

### 5.3 独立文档

明确代码版本与覆盖范围 → Git 准备 `docs_{说明}` → 文档更新 → 事实核对与审查 → 合并 → 文档任务验收。

上游合入引起的更新可关联同步记录或提交范围。创建文档任务及分支名称允许无来源开发任务编号。

## 6. 确认权限与失效

默认允许任务创建者和项目负责人确认。确认者必须是当前工作区的有效成员，并有当前任务访问权。项目负责人为现有 project.lead_type 为 member 对应的 lead_id。每次请求在服务端重新校验。

智能体创建的子任务从主任务关联创建者取得默认确认责任。缺少可确认的人类创建者和项目负责人时显示“待设置确认负责人”，引导成员配置项目负责人。任务级指定确认人留待后续扩展。

设计、计划和归档各自提交不可变的产出版本。确认请求携带 expected_revision 和 artifact_version，过期版本返回冲突与当前版本提示。同一版本重复确认返回已有结果。

| 变化 | 失效范围 | 后续处理 |
| --- | --- | --- |
| 需求范围、验收标准变化 | 受影响设计、计划、测试及归档确认 | 展示影响清单，重新提交相关产出 |
| 设计内容或输入规格版本变化 | 设计及依赖它的计划确认 | 先确认新设计，再确认计划 |
| 任务范围、依赖或角色交付变化 | 计划确认 | 停止受影响的后续派发，重新确认计划 |
| 实现提交变化 | 对应测试证据与归档清单有效性 | 补充相关验证，重提归档清单 |
| 发布版本、环境或执行配置变化 | 发布执行授权与相应验证 | 展示差异并重新授权 |
| 归档清单或待合并规范变化 | 归档确认 | 重新确认清单 |

失效后保留历史确认，当前有效指针指向新版本。已运行任务保留原上下文，受影响执行按现有暂停与需求变更机制停止或等待，不自动丢弃产出。

## 7. 接口设计

以下为已实施接口，服务端复用现有成员权限、revision 冲突响应和审计机制。

| 方法与资源 | 行为 |
| --- | --- |
| GET / PUT `/api/workspaces/{id}/onespec` | 读取或保存默认运行时，写入限工作区 owner/admin |
| GET / PUT `/api/projects/{id}/onespec` | 保存启用状态、运行时模式、总览代码库 |
| POST `/api/projects/{id}/onespec/team` | 幂等解析或配置预置团队 |
| GET `/api/issues/{id}/onespec` | 获取阶段、产出版本、确认与待处理事项 |
| POST `/api/issues/{id}/onespec/artifact` | 提交设计、计划、测试或归档清单版本 |
| POST `/api/issues/{id}/onespec/decision` | 有权成员确认或退回具体版本 |
| POST `/api/issues/{id}/onespec/advance` | 校验阶段条件并推进阶段 |
| POST `/api/issues/{id}/onespec/git` | 记录、领取和完成本任务允许的 Git 操作 |

产出写入允许当前阶段被授权的智能体和有权成员。确认入口只接受人类身份。advance 允许 OneSpec 或有权成员调用，并由服务端检查确认、依赖和运行状态。

补充动作包括 `start`、`kind`、`run`、`reopen`、`refresh-configuration` 与 `release-draft`。CLI 对应 `multica issue onespec <action> <issue-id> --file <JSON>`，查询使用 `get`。

设计与计划都能保存草稿。只有已确认计划可以调用子任务应用逻辑。计划应用在一个事务中创建子任务、记录关联并更新流程版本，重复请求依靠已有幂等键返回同一结果。

现有 `/execution-plan` 对 OneSpec 任务调用同一确认检查。旧任务维持已有行为，任务是否启用 OneSpec 由其持久化流程记录决定，客户端参数不能临时绕过阶段规则。

## 8. 调度、重试与执行边界

阶段转换与相关任务状态在同一事务中提交。运行当前阶段通过独立 `run` 动作，在同一事务中分配负责人并入队。队列保存阶段及 generation，子任务保存已确认计划版本。入队、领取和重试核对有效快照，过期请求被拒绝。

同一任务阶段只允许一个有效执行实例。操作幂等键关联任务、阶段和产出版本。进程中断后检查已保存的执行及产出，能够继续时恢复同一实例。

数据库与接口约束保障通过 Multica 发起的阶段执行。拥有终端权限的智能体仍能够自行运行命令，首轮通过阶段 Skill、任务范围与运行记录约束其行为。对任意 shell 命令的全面隔离需要独立的执行沙箱能力。

## 9. Git 管理落地

Git 管理 Skill 根据记录生成确定分支名，并在执行前调用 Git 检查仓库状态和分支有效性。

| 类型 | 名称与动作 |
| --- | --- |
| 开发 | 从 `release` 的固定提交创建 `release_{task_id}` |
| 缺陷 | 从已选择的修复基准创建 `hotfix_{日期}{task_id}` |
| 文档 | 创建 `docs_{说明}`，记录代码事实基准 |
| 上游同步 | 由 `main` 创建 `main_{日期}`，同步并验证后集成到 `release` |

日期暂按项目时区的 YYYYMMDD 设计。任务标识使用稳定系统 ID，在页面同时显示可读编号。日期格式和标识编码是本设计的建议取值。

工作目录按仓库与任务隔离。检测到已有分支时核对操作记录和基准，确认属于当前任务后复用。同名分支来源不明时进入等待处理。

发布后回合限定实际发布提交范围。`release` 变化时重新准备合并结果，涉及语义的冲突交开发处理并回归。操作记录区分发布成功、待回合和回合成功。

Git 推送、合并和标签操作读取项目策略与已有任务授权。未配置策略时准备可审查改动并请求具体操作确认。实际合并方式在 Git 策略评审后固定。

## 10. Skill 适配与分发

以本地发布包为源，按角色选择并适配 Skill，完整保留必要参考资料和模板。平台内置包通过现有 claim/bundle 分发机制提供，记录版本和内容摘要。

新增 OneSpec 编排、Git 管理、发布执行能力。开发负责 `onespec-task` 与 `onespec-complete`，工程文档由独立任务调用 ai-readme 系列。

适配后的 Skill 统一使用 Multica 任务上下文和本地文档输入，查询阶段确认后继续执行。测试角色输出实际测试结果和证据，提测模板中的凭证以引用或脱敏值表示。

启动时检查必需 Skill 文件和工具能力，缺失时显示具体处理入口。内置 Skill 使用明确的平台命名空间，同名用户 Skill 在初始化时提示冲突并要求选择，避免加载内容不确定。

确认按钮展示本次确认对象和版本，退回要求原因。无权限成员可查看阶段与有权处理人。对话回复提供上下文，正式确认通过带版本的操作提交。

## 12. 兼容与启用

现有项目提供“启用 OneSpec”入口，可查看项目当前角色绑定并初始化预置团队。保存配置后，新任务使用新流程。已有待办任务可以通过任务面板显式接入。运行中任务保留原版本，完成或暂停后再处理接入。

旧六角色配置按原键读取，新角色缺省为未配置，通过启用流程补齐。现有安全角色继续保留。新增字段有默认值，接口写入使用显式字段和 revision，避免旧客户端覆盖新配置。

工作区 OneSpec 配置独立持久化，避免现有 workspace.settings 整体更新覆盖默认运行时。双向迁移执行前核对当前迁移编号，SQL 变更后运行 `make sqlc`。

本次实施按用户指定在 `release_V1.0_vibe-coding` 分支开发，计划编制时基准提交为 `6a357f34d`。后续由 OneSpec 管理的新任务采用已确认的分支规范。

## 13. 验证与交付标准

| 验证层 | 必须覆盖 |
| --- | --- |
| 规则测试 | 默认值解析、确认依赖失效、轻量流程选择、分支命名 |
| 数据库接口测试 | 权限隔离、revision 冲突、重复初始化、重复确认、计划应用重试 |
| 阶段执行测试 | 未确认计划无法派发、过期任务无法领取、运行时切换不影响已有运行 |
| 前端组件测试 | 继承配置、确认人展示、退回原因、等待入口、文档版本冲突 |
| 浏览器流程 | 简单代码改动、无服务器发布准备、独立文档更新三条路径 |
| 现有行为回归 | 原项目角色、任务执行、需求变更和发布验收 |

先用隔离工作区与受控测试运行时验证流程和真实入口，真实智能体与服务器测试按具体任务授权执行。测试中记录实际执行与跳过项。

功能交付应提供可运行页面和接口、完整 Skill 包、迁移及回滚、验证结果、已知限制，并将发布版本与提交关联。详细设计确认后再拆分实施任务及逐项验收清单。
