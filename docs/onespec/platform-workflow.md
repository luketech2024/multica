# Multica OneSpec 流程方案

评审草案 · 2026-11-11

本文整理本次讨论确认的产品方向，并提出阶段与交接规则。标为“建议”的内容等待评审。目标能力需要后续实现，本文尚未成为运行时生效规则。

配套文档包括 [角色与 Skill 分工](agent-skills.md) 和 [Git 分支管理规范草案](git-workflow.md)。

## 1. 已确认的设计基线

- 平台提供预置 OneSpec 团队，工作区配置授权的运行时和资源，普通用户直接使用。
- OneSpec Agent 承接调度职责，负责识别任务类型、选择流程、组织交接、跟踪进度和必要确认。
- 产品、开发、测试、运维、项目文档、Git 管理分别承担专业工作。
- 开发负责设计、任务拆解、实现和规格归档，包括 `onespec-task` 与 `onespec-complete`。
- OneSpec 文档保存在对应代码库的 `onespec/` 下，由 Git 管理版本。Multica 管理任务、阶段状态和确认记录，并关联文档路径与提交。
- ai-readme 使用独立文档任务、分支和审查流程。开发根据变更规模、影响范围与上线时机安排更新，可以集中覆盖多个开发任务。
- 创建项目时允许缺少部署目标。机器、凭证等执行信息在部署前补齐。
- 设计、计划和归档分别请求人工确认，各自记录产出版本与确认结果。
- 确认默认由任务创建者完成，项目负责人可以代为确认。任务指定确认人的能力作为后续扩展。
- 工作区管理员配置默认运行时，新项目继承默认值，项目可以单独调整。
- 项目配置用于保存多仓库任务总览的指定代码库，各业务代码库保存自己的规格和实现文档。
- 业务主分支为 `release`，开发使用 `release_{task_id}`，缺陷使用 `hotfix_{日期}{task_id}`，代码发布后回合 `release`。Fork 项目使用 `main` 跟踪上游，经 `main_{日期}` 同步并集成到 `release`。

## 2. 资产与职责

| 层次 | 管理内容 |
| --- | --- |
| 平台 | 预置角色、流程定义、Skill 包及版本 |
| 工作区 | 默认运行时、可使用的运行时、成员权限、团队补充规则 |
| 项目 | 业务代码库、总览指定代码库、项目运行时设置、应用、角色绑定、Git 策略及部署配置 |
| 任务 | 本次规格、执行计划、分支、产出、确认和验证记录 |

建议把平台角色规则与工作区补充指令分别保存，执行时记录有效版本。平台规则更新应用于后续运行。已有运行保留启动时的版本记录，重试是否升级由任务显式决定。

工作区管理员设置默认运行时，新项目继承该设置，项目可以选择其他已授权运行时。实际执行时检查访问权限和运行时可用性，并记录本次使用的运行时。默认值调整如何影响已有项目，在详细设计中明确。

## 3. 按任务类型选择流程

| 类型 | 默认经过的阶段 | 所需规格 |
| --- | --- | --- |
| 新功能 | 需求、设计与计划、实现、测试、交付、按需发布、验收 | Proposal、Delta Spec、设计和任务计划 |
| 简单代码调整 | 简短需求、轻量计划、实现、验证、交付、验收 | 可判定的范围与验收条目，按轻量模式维护文档 |
| 缺陷修复 | 复现与根因、修复计划、修复、回归、交付、按需发布 | 缺陷事实、验收标准与修复计划 |
| 发布已有版本 | 发布目标确认、发布准备、环境检查、部署、运行验证、验收 | 发布范围、版本选择规则和完成标准 |
| ai-readme 更新 | 确定代码基准、文档更新、事实核对、审查与合并 | 独立文档任务中的范围和完成标准 |

OneSpec 展示所选流程及原因。用户可以调整任务类型。流程允许多个任务并行，单个仓库的写入归属遵循 Git 规范。

## 4. 阶段输入与完成条件

| 阶段 | 负责人 | 输入 | 产出与完成条件 |
| --- | --- | --- | --- |
| 接收任务 | OneSpec | 用户目标和项目上下文 | 确定任务类型、下一步及待澄清项 |
| 整理规格 | 产品 | 原始需求、已知约束 | 保存规格与验收条目，用户确认对应版本 |
| 准备工作目录 | Git 管理 | 仓库、任务及分支策略 | 记录基准提交、工作分支与 worktree |
| 设计 | 开发 | 已确认规格、代码现状 | 生成设计，用户确认对应版本后进入计划阶段 |
| 计划 | 开发 | 已确认设计，或轻量模式的已确认规格 | `tasks.md` 覆盖验收条目，用户确认计划版本后进入实现 |
| 实现 | 开发 | 任务计划及隔离工作目录 | 代码、构建和自检结果，明确未完成事项 |
| 验证 | 测试 | 规格版本及可复现代码版本 | 逐项结论、执行命令与证据，失败项关联修复任务 |
| 交付与归档 | 开发、Git 管理 | 验证结果、归档清单和交付范围 | 用户确认归档清单后，开发执行归档，Git 管理组织提交与审查并记录发布候选版本 |
| 发布准备 | 运维 | 发布范围及版本 | 发布草稿、待补配置、部署与回退步骤 |
| 部署 | 运维 | 已授权发布单及完整执行配置 | 实际部署结果和运行验证证据 |
| 发布后回合 | Git 管理、开发、测试 | 实际发布提交及当前 `release` | 处理冲突和适用验证，将已发布变更合并回 `release`，记录结果 |
| 成果验收 | 用户 | 对应版本的交付和证据 | 验收通过或退回原因 |

文档写入前需要可访问的代码库及受控工作目录。项目尚未配置仓库时，需求草稿可先保存在 Multica，绑定代码库后落盘并记录对应版本。

多仓库任务的总览保存在项目指定代码库中，作为各仓库规格、计划和交付记录的统一入口。该代码库通过项目配置明确选择，任务记录本次采用的代码库及总览路径。

指定代码库保存项目级需求总览、跨仓库依赖和交付索引。各业务代码库保存自己的 Spec、设计、`tasks.md` 和实现记录。单仓库项目可以选择自身作为总览代码库。

建议总览路径采用 `onespec/changes/<feature-name>/overview.md`，记录参与仓库、子任务、规格路径、依赖和交付提交。各仓库文档引用使用仓库标识、相对路径和提交版本。此路径及字段为详细设计建议。

指定代码库尚未配置时，可以继续整理项目需求，创建多仓库总览前补齐配置。调整指定代码库时，已有任务保留原有引用，迁移另行记录目标位置与版本。

建议将验收标准分为代码交付和部署结果等适用范围。代码任务可以在发布前完成验收，部署任务在部署验证后验收。创建发布草稿允许关联尚在执行中的部署任务，避免该任务与发布单互相等待。

规格归档发生在相关实现和验证完成后。关联发布与验收状态继续保存在 Multica，归档记录自身的完成状态单独可查。

代码任务按照发布后回合规则推进。发布成功但尚未回合时显示待回合，实际发布结果单独保留。独立文档任务按文档审查与合并流程完成。已按范围完成验收的代码任务，其后续发布与回合事项继续通过关联记录追踪。

## 5. 缺失信息与等待

| 缺失项 | 可继续的工作 | 必须补齐的节点 |
| --- | --- | --- |
| 业务目标、完成标准 | 收集背景和澄清问题 | 需求确认 |
| 代码库 | 整理需求草稿 | 本地规格落盘、代码分析与实现 |
| 开发所需环境 | 规格整理和可独立完成的分析 | 依赖该环境的执行 |
| 测试环境 | 用例与测试计划 | 对应测试执行 |
| 服务器、域名、凭证 | 发布目标确认和发布草稿 | 使用这些配置的部署执行 |
| ai-readme 更新 | 开发、测试、发布按各自条件推进 | 独立文档任务的完成验收 |

等待记录应包含缺少的具体信息、受影响阶段、处理人、补齐入口和可继续事项。OneSpec 汇总一次明确请求，收到补充信息后从相应阶段继续。

## 6. 确认和交接

确认默认由任务创建者完成，项目负责人可以代为确认。界面显示可确认人员，后端校验实际操作者权限，记录确认人及其身份。后续支持在任务中指定确认人，具体配置和权限规则在扩展设计时确定。

确认记录关联任务、文档或发布单版本、确认人、时间和授权范围。Skill 读取已生效的确认，阶段内重复执行复用该记录。范围或目标版本改变时，系统识别受影响内容并重新请求相应确认。

设计、计划、归档采用逐项确认。设计确认后进入计划，计划确认后进入实现，归档清单确认后执行规范合并与归档。任务总体授权不能代替这三项确认。轻量流程按已选定的阶段请求确认，省略设计阶段的依据保存在任务记录中。

建议每次交接记录以下信息。

- 任务、项目、代码库、分支、worktree 和基准提交。
- 当前规格版本、验收条目及确认记录。
- 输入文件、输出文件、产出所属提交。
- 实际检查结果、日志或报告位置。
- 待解决问题、责任角色和可继续的工作。

Multica 管理调度状态，`tasks.md` 保存开发计划与交付记录。建议为本地任务项建立稳定标识，与 Multica 子任务关联。更新失败应显示“状态待同步”及原因，恢复后补齐。

智能体运行结束后，系统检查对应阶段要求。页面分别展示运行结果与阶段完成情况，缺少交付物时显示待补交付。

## 7. 独立文档更新流程

开发在完成变更或准备发布时判断工程文档是否需要更新，可以立即安排或集中到后续版本。OneSpec 记录待更新项并提醒，由开发决定启动时机。

文档任务包含目标代码版本、覆盖的变更范围、受影响文档和审查要求。变更来源可以关联开发任务，也可以通过上游同步记录或提交范围追溯。项目文档 Agent 在独立 worktree 中核对指定代码，更新工程知识。Git 管理 Agent 使用 `docs_{说明}` 命名独立文档分支，组织提交和合并。

Spec、设计和 `tasks.md` 仍随开发任务维护。ai-readme 文档任务可以聚合多项变更，并明确自己的完成状态。

## 8. 验收场景

| 场景 | 预期结果 |
| --- | --- |
| 新用户使用默认团队 | 连接工作区默认运行时后，可以直接创建和推进任务 |
| 项目继承或调整运行时 | 新项目继承工作区默认运行时，项目可单独选择已授权运行时 |
| 创建者确认或负责人代为确认 | 两种身份都能提交确认，记录实际操作者并由后端校验权限 |
| 初建项目没有机器 | 发布目标可确认，可保存发布草稿，部署前提示补齐机器 |
| 发布任务尚未验收 | 可以建立关联发布草稿，部署验证后完成任务验收 |
| 简单文案修改 | 使用轻量规格和计划，交付可验证的修改 |
| 测试发现问题 | 失败证据返回开发，修复后复测受影响条目 |
| 已确认后重试执行 | 复用仍有效的确认记录，避免重复索要同一确认 |
| 五个变更集中更新文档 | 一个文档任务关联五项变更，在独立分支交付 |
| 发布完成但文档待更新 | 发布结果正常记录，待更新项保留独立状态 |
| 设计、计划、归档逐项确认 | 每项确认绑定对应版本，满足当前项确认后推进到下一步 |
| 多仓库任务生成总览 | 总览写入项目指定代码库，能追溯各仓库文档和交付版本 |

## 9. 本轮评审结论

1. 设计、计划与归档采用逐项确认。
2. 项目增加指定代码库配置，用于保存多仓库任务总览。
3. 确认失效规则方向评审通过。详细设计列出代码、规格和发布结果变化对各类确认的影响表。
4. 阶段状态映射与等待处理入口方向评审通过。详细设计补齐与现有任务状态的转换表及入口行为。
5. 默认由任务创建者确认，项目负责人可代为确认，后续支持任务指定确认人。
6. 增加工作区默认运行时设置，新项目继承，项目可以单独调整。
7. 指定代码库保存项目级需求总览、跨仓库依赖与交付索引，各业务仓库保存自身规格和实现记录，单仓库项目可选择自身。

本节记录流程方案及后续补充评审结论。Git 分支名称、发布后回合和 Fork 同步路径按后续确认更新，其他 Git 建议参见配套规范的待评审清单。
