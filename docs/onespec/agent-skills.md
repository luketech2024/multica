# OneSpec 角色与 Skill 分工方案

评审草案 · 2026-11-11

本文与 [流程方案](platform-workflow.md)、[Git 规范草案](git-workflow.md) 配套。角色归属采用讨论确认的分工，分发与版本机制为实施建议。

## 1. 来源与适配范围

本次参考发布包为 `C:/Users/luke/Desktop/ai-coding-skill-release_v2.0.0/codex`。该目录包含 28 个 Skill，带有 `SKILL.md`、参考资料和输出模板。

已核对发布包清单与关键 Skill 入口。各 Skill 的全部引用资料、运行时兼容性以及端到端行为需要在适配实施中验证。

目标流程使用 Multica 任务与本地代码库中的文档。按角色选用需求、设计、实现、测试、归档和工程文档 Skill，统一读取任务上下文与本地文件，产出写入代码库并由 Git 管理版本。

## 2. 角色与能力

| 角色 | 工作职责 | 复用或新增能力 |
| --- | --- | --- |
| OneSpec | 识别任务、选择流程、检查阶段产出、协调交接和确认 | 新增流程编排 Skill，读取平台阶段与授权记录 |
| 产品 | PRD、Proposal、Delta Spec、验收条目及按需原型 | `onespec-generate-prd`、`onespec-change`、`onespec-generate-prototype` |
| 开发 | 技术设计、任务拆解、实现、自检、缺陷分析与修复、规格归档 | `onespec-design`、`onespec-task`、`onespec-implement`、`onespec-complete`、缺陷修复系列 |
| 测试 | 生成用例、执行验证、记录失败及复测结果 | `onespec-testcase`、`onespec-checklist`、`onespec-bug-checklist`，补充测试执行与证据交付约定 |
| 项目文档 | 在独立任务中维护工程文档、检查文档与代码一致性 | `ai-readme`、`ai-readme-cocreate-doc`、`ai-readme-code-review`、`ai-readme-workspace`、`onespec-product-wiki` |
| Git 管理 | 工作目录、分支、提交、合并、冲突协调及授权推送 | 新增 Git 工作流 Skill，使用项目有效分支策略 |
| 运维 | 发布准备、配置检查、部署、运行验证和回退 | 新增发布 Skill，对接 Multica 发布单与部署结果 |

各角色按技术栈选用 `onespec-std-*`。加载时只选与本次任务相关的规范和参考资料。

Git 管理 Agent 使用 `release` 作为业务主分支，开发和缺陷分别使用 `release_{task_id}` 与 `hotfix_{日期}{task_id}`，发布后组织回合。Fork 项目通过 `main` 与 `main_{日期}` 管理上游同步，并协调合入 `release` 时的冲突处理和验证。

开发产出 `tasks.md`，OneSpec 按计划协调执行。开发使用 `onespec-complete` 处理主规范与变更归档，OneSpec 检查归档条件并安排执行。

设计、计划和归档分别确认。OneSpec 将各项产出交用户评审，并把对应版本的确认记录传给执行角色。多仓库任务从项目配置读取总览指定代码库，在该库维护总览，各业务仓库维护自己的文档与实现。

OneSpec 默认请求任务创建者确认，项目负责人可以代为确认。各执行角色读取实际确认人与产出版本的记录，后续按任务指定确认人的配置扩展。

## 3. 必须适配的行为

| 源包行为 | Multica 适配目标 |
| --- | --- |
| `onespec-design` 产出设计并等待审查 | 展示设计版本，用户逐项确认后进入任务计划阶段 |
| `onespec-implement` 要求回复“开始” | 读取对应任务与规格版本的有效执行授权，缺少授权时进入待确认 |
| `onespec-task` 产出计划后等待审查 | 展示计划版本，单独确认后交给实现角色 |
| `onespec-complete` 要求归档确认 | 展示归档清单，单独确认后执行，记录合并规范的版本和位置 |
| 本地任务状态写在 `tasks.md` | 维护本地任务项与 Multica 子任务映射，分别记录交付事实和调度状态 |
| 缺陷修复输入与结果记录 | 从 Multica 缺陷或用户材料读取事实，在代码库保存修复计划和验证结果，关联对应任务 |
| 测试清单输入与产出 | 读取 Multica 任务集合及本地规格，在代码库保存测试清单与证据，关联对应任务 |
| 提测清单要求配置不脱敏 | 使用配置引用，对凭证值脱敏，报告真实检查结果 |
| 各角色分别询问缺失信息 | OneSpec 汇总问题，标记影响阶段和责任人 |

平台适配版应明确替换源包中的旧行为，供执行端读取同一份有效规则。代码中记录成功、失败、等待和授权的逻辑，与 Skill 对这些状态的描述保持一致。

## 4. 平台资产与执行环境

建议将平台预置定义、工作区补充配置、任务执行上下文分层保存。平台提供默认角色与 Skill 包，工作区选择有权使用的运行时、账号和资源，任务提供本次职责及文档版本。

工作区管理员配置默认运行时，新项目继承，项目可以单独调整。平台角色执行时使用项目解析出的已授权运行时，执行记录保存实际选择。现有智能体绑定与项目运行时设置的衔接在详细设计中明确。

Skill 包需要整体分发 `SKILL.md`、`references/`、`assets/` 等依赖。建议每个发布版本记录内容摘要、适用角色和验证过的运行时，在启动时核对。

当前四个已有智能体绑定 Cursor。发布包来自 `codex` 目录，接入时需要验证 Cursor 的加载路径、引用文件和工具调用方式，再扩展到其他运行时。

旧智能体迁移需列出当前指令与平台版本的差异，保存原配置和项目绑定。项目已有任务的团队快照也需要明确处理，未开始或尚未确认的任务可提供同步入口，执行中的任务保留其已记录配置。

## 5. 选择角色的建议

采用“推荐适配角色 + 显示其他可用智能体”的交互。角色用途用于排序和说明，同一个智能体可以按项目需要兼任。

访问权限、归档状态和绑定运行时由后端校验。角色职责与指令冲突显示具体原因及调整入口。指令冲突提示的准确性需要验证，不能仅凭名称推断能力。

## 6. 交付检查

- 每个 Skill 交付文件及其对应任务、仓库、规格版本。
- 测试结果包含实际命令、目标代码版本和证据，未执行项单独记录。
- 重试可以识别已有产出和确认，避免重复建任务或覆盖人工修改。
- 工程文档任务保留来源代码版本和覆盖范围。
- 发布 Skill 通过已有授权的发布执行入口操作，并记录结果与失败原因。
