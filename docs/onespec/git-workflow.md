# OneSpec Git 分支管理规范草案

评审草案 · 2026-11-11

本规范服务于 [OneSpec 流程](platform-workflow.md) 和 [角色分工](agent-skills.md)。主分支、开发与缺陷及文档分支命名、发布后回合以及开源同步路径已确认。合并方式和授权策略等标为建议的内容继续评审。

## 1. 管理对象

一个项目可以包含多个代码库。Git 策略按代码库配置，任务记录仓库标识、基准分支与提交、工作分支、工作目录、目标合并分支和交付提交。

项目指定一个代码库保存多仓库任务总览。Git 管理 Agent 为该库记录相应工作分支与提交，并将总览引用关联到各业务仓库的实际交付版本。任务总览随开发协作维护，ai-readme 继续使用独立文档任务。

业务主分支统一为 `release`。开发分支使用 `release_{task_id}`，缺陷分支使用 `hotfix_{日期}{task_id}`。Fork 项目另外使用 `main` 跟踪开源上游，并通过 `main_{日期}` 集成上游更新。

| 分支用途 | 名称 | 创建来源 | 合并目标与时机 |
| --- | --- | --- | --- |
| 业务主分支 | `release` | 项目选定的初始基准 | 接收发布后的任务变更及验证后的上游集成 |
| 开发 | `release_{task_id}` | `release` 的明确提交 | 发布成功后合并回 `release` |
| 缺陷 | `hotfix_{日期}{task_id}` | 建议以 `release` 中对应待修复版本的提交为基准 | 修复发布成功后合并回 `release` |
| ai-readme 文档 | `docs_{说明}` | `release` 的明确提交 | 文档独立审查通过后合并回 `release` |
| 开源跟踪 | `main` | Fork 对应的上游分支 | 跟踪开源代码，作为同步分支的来源 |
| 开源同步 | `main_{日期}` | `main` 的明确提交 | 同步上游、完成集成验证后合并到 `release` |

`task_id` 使用 Multica 中稳定且可用于分支名的任务标识。日期格式建议采用项目时区下的 `YYYYMMDD`，例如 `hotfix_20261111TEST-10` 和 `main_20261111`。日期与任务标识的具体编码在详细设计中确定。

实际仓库已有的 `release_V1.0_vibe-coding` 记录为现有分支。接入新规范时，需要明确用于初始化 `release` 的提交及现有任务分支映射。

## 2. 分支与工作目录

Git 管理 Agent 在开始前检查仓库状态、已有任务绑定和未提交改动，确认基准提交后创建或复用任务工作目录。

并行任务建议使用独立 worktree。串行子任务可以复用同一个任务分支和工作目录，由 OneSpec 确认上一写入者已完成交接。分支和目录操作归 Git 管理 Agent 统一组织。

重试时先检查已记录的分支、目录和提交，恢复已有工作。发现无法确认归属的改动时，保留现场并说明需要确认的内容。

## 3. 开发与 Spec

产品和开发生成的 PRD、Proposal、Delta Spec、设计和任务计划保存在对应代码库的 `onespec/` 下，按当前任务的分支管理。

开发负责实现和本地验证，交付改动范围、自检结果、规格更新和未完成项。Git 管理 Agent 核对归属后组织提交。

建议提交采用仓库已有的 Conventional Commits 约定，任务记录保存提交关联。一次提交围绕可审查的变更组织，避免把独立任务的修改混入同一次交付。

开发在归档条件满足后执行 `onespec-complete`，Git 管理 Agent 将规范合并与归档文件变化纳入对应交付记录。

设计、计划和归档各自经过人工确认。Git 管理 Agent 在组织归档变更时核对已确认清单及版本，代码提交或合并授权与归档确认分别记录。

## 4. ai-readme 独立文档任务

开发根据变更规模、架构影响与上线安排选择更新时机。可以为单次大改立即创建文档任务，也可以在一个版本发布后汇总多项变更。

文档分支使用 `docs_{说明}`，说明概括本次更新范围，例如 `docs_upstream-agent-workflow`。上游 `main` 的功能合入后，可以据此发起文档更新，分支命名无需任务编号。Git 管理 Agent 校验说明组成的分支名有效，并检查已有同名分支的归属。

每个文档任务应记录以下内容。

- 覆盖的变更范围，以及对应的开发任务、上游同步记录或提交范围。有来源任务时记录任务关联。
- 用于事实分析的代码提交或发布标签。
- 文档分支的合并目标及基准提交。
- 需要更新的 `AGENTS.md`、`docs/ai-readme/` 或其他工程知识文档。
- 审查人或审查角色，以及完成标准。

代码事实基准和文档合并目标分别记录。例如任务分析已发布版本，而 `release` 已经包含其他发布或上游更新，需要核对目标差异并明确文档适用版本。Git 管理 Agent 在合并前检查这两个基准是否仍符合任务范围。

项目文档 Agent 在独立 worktree 中修改文档，核对代码事实，区分自动生成事实与人工维护的业务知识。Git 管理 Agent 组织文档提交与审查。开发发布进度与文档更新进度分别追踪，OneSpec 保留待更新提醒。

如果文档任务发现代码行为有问题，应建立关联问题并交开发判断。文档交付范围通过审查记录确认。

## 5. 测试、合并与冲突

测试记录绑定被验证的代码提交和规格版本。合并前检查目标分支是否变化，对会影响已有验证的差异安排相应回归。

Git 管理 Agent 处理能够明确判断的文件合并。涉及业务语义的冲突交开发，涉及规格范围的冲突由产品与开发确认，工程文档冲突交文档角色核对对应代码版本。

建议由项目明确默认合并方式。Squash、merge commit 或其他方式的选择需要评审，执行后记录源提交与最终提交的关联，保证测试和发布证据可追溯。

## 6. 发布与缺陷修复

开发流程按 `release` → `release_{task_id}` → 测试 → 发布 → 回合 `release` 执行。发布单引用任务分支中的明确提交和产物标识，部署期间分支继续变化时，已选定发布版本保持可追溯。

缺陷流程使用 `hotfix_{日期}{task_id}`，完成适用验证和修复发布后回合 `release`。Git 管理 Agent 记录创建基准、实际发布提交与回合结果。

发布成功后，任务进入待回合阶段，Git 管理 Agent 核对任务分支是否新增尚未发布的改动，以及 `release` 是否已经变化。回合范围限定为本次已发布的变更。涉及其他任务或上游更新的冲突，需要相关角色确认并完成适用验证后合并。

发布结果和回合结果分别记录。发布成功但回合失败时，保留发布事实并展示待处理原因。回合提交与实际部署提交分别保存，保证线上版本可以准确定位。

发布标签名称、创建时机和推送权限由项目策略确定。部署执行授权与 Git 推送授权分别记录。

## 7. Fork 项目的开源同步

`main` 承载 Fork 对应的开源代码，业务开发以 `release` 为基准。项目记录开源上游地址、对应分支以及本地跟踪分支 `main`。

每次同步使用 `main_{日期}`。Git 管理 Agent 从已记录的 `main` 提交创建或恢复该分支，读取上游目标提交并同步更新，记录本次差异。

建议将同步中确认的上游版本推进到 `main`，保持其开源跟踪用途。集成到业务代码时，在基于当前 `release` 的隔离工作目录中合并 `main_{日期}`，协调开发解决业务冲突、测试验证合并结果，再完成对 `release` 的更新。保留上游目标提交、同步分支提交与最终集成提交的关联。

同一天再次同步时，先检查已有 `main_{日期}` 的状态。已完成同步后又需要引入新的上游版本，应等待明确分支复用或命名规则，避免覆盖已有执行记录。同步周期、同日重复同步方式以及上游集成后的发布安排列入待评审项。

## 8. 权限与恢复建议

项目策略明确本地提交、远端推送和合并的授权方式。已有任务授权覆盖的操作复用相应记录，超出范围时由 OneSpec 汇总确认。

共享分支历史调整、标签变更、分支清理等操作需要明确目标及恢复依据。正常开发采用新增提交和可追溯合并。失败后保留分支、worktree 和日志，恢复时从最后已验证状态继续。

## 9. 规范验收

| 场景 | 通过标准 |
| --- | --- |
| 两个开发任务并行 | 工作目录和改动归属清晰，提交各自对应任务 |
| 多项变更统一更新文档 | `docs_{说明}` 分支记录来源任务或上游同步记录、提交范围与目标代码版本 |
| 上游功能没有开发任务编号 | 可使用 `docs_{说明}` 创建文档分支，通过上游同步记录及提交追溯范围 |
| 文档基于旧发布版本 | 核对 `release` 的新差异后明确文档适用范围 |
| 任务重试 | 能恢复原有分支和提交记录 |
| 合并出现语义冲突 | 责任角色确认处理结果，相关验证重新执行 |
| 开发任务发布 | 从 `release_{task_id}` 的明确提交发布，发布后回合 `release` |
| 缺陷修复上线 | `hotfix_{日期}{task_id}` 的发布与回合状态均可追溯 |
| 发布成功但回合失败 | 展示待回合原因，保留真实部署版本与发布结果 |
| Fork 上游同步 | 通过 `main_{日期}` 同步上游，解决集成冲突并验证后合并到 `release` |

## 10. 待评审决定

1. 日期格式、任务标识编码及现有分支迁移基准。
2. 默认合并方式，提交、推送、合并和发布标签的授权策略。
3. 多仓库任务分别交付、汇总验收的规则。
4. ai-readme 集中更新的提醒节点和责任人。
5. 开源同步周期、同日重复同步方式、`main` 推进方式与上游集成后的发布安排。
